## 문서 목적

이 문서는 대신고에서 사용자가 **교통위반 상황을 설명한 순간부터 AI가 장시간 블랙박스 영상을 탐색하고, 사건 후보와 신고자료를 준비하며, 사용자가 필요한 부분만 확인·수정하여 신고 준비를 완료하는 전체 흐름**을 정의한다.

이 문서는 세부 화면 디자인이나 기술 구현 명세가 아니다.

핵심적으로 다음을 정의한다.

* 사용자가 어떤 일을 AI에게 맡기는가
* AI가 어떤 범위까지 자동으로 처리하는가
* 사용자가 언제 확인하거나 개입하는가
* AI 결과가 불확실하거나 시스템이 실패했을 때 어떻게 복구하는가
* 신고자료가 어떤 상태가 되면 안전신문고 제출 단계로 넘어가는가

구체적인 화면 컴포넌트와 세부 마이크로카피는 `modules/web/ux/`, 실제 모델·모듈 구현과 상태값은 각 모듈 문서에서 관리한다.

## 1. 핵심 AI UX 원칙

대신고의 사용자 경험은 다음 구조를 따른다.

> **사용자 목표 → AI에게 위임 → 작업 상태 관찰 → 필요한 순간에만 개입 → 최종 확인**

AI가 많이 개입하는 것 자체가 목표가 아니다.

사용자가 원래 직접 해야 했던

`긴 영상 다시 보기 → 사건 찾기 → 필요한 구간 자르기 → 번호판·시간·위치 확인 → 신고자료 준비`

과정에서 반복적이고 시간이 많이 드는 부분을 AI가 대신하고, 사람은 **자신만이 판단할 수 있거나 오류 비용이 큰 부분**에 집중하도록 한다.

### AI는 다음을 담당한다

```text
사용자 기억 단서 이해
→ 우선 탐색 범위 구성
→ 사건 후보 탐색
→ 후보 비교·검증
→ 사건 근거 정리
→ 번호판 후보 추출
→ 발생시각 확인
→ 위치 정보 보강
→ 신고유형 추천
→ 신고용 파생영상 생성
→ 신고요건 검사
→ 신고자료 정리
```

### 사용자는 다음을 담당한다

```text
내가 찾던 사건이 맞는가?
AI가 이해한 기억 단서가 맞는가?
불확실한 번호판이 맞는가?
AI가 설명한 사건 상황이 내가 본 것과 맞는가?
최종 신고자료가 실제 상황과 맞는가?
실제로 신고할 것인가?
```

AI는 법적 위반 여부를 최종 확정하거나 사용자 승인 없이 신고를 제출하지 않는다.

# 2. 기본 화면 구조

`[프로토타입]` **대신고는 대화형 작업공간(Conversational Workspace)이 아니라 단계형 구조 화면을 사용한다.** 1.2까지 유지되던 `대화형 작업공간` 구조는 목업·프로토타입 단계에서 폐기했다.

자연어는 **§5 「기억 단서 입력」 한 곳에서만** 받는다. 그 이후의 모든 보정과 판단은 **명시적인 버튼과 입력칸**으로 한다.

폐기한 이유는 셋이다.

1. 중요한 판단은 사용자가 **원본·근거를 직접 보고** 확인해야 한다. 채팅 답변으로 대신할 수 없다.
2. 채팅 로그는 되돌아가 고치기 어렵다. 이 제품은 되돌아가 고치는 일이 잦다(§9).
3. 자연어 보정은 「무엇이 유지되고 무엇이 바뀌는지」를 사용자에게 보장하지 못한다. 버튼은 보장한다.

바뀐 것은 **입력 수단**이지 원칙이 아니다. 아래 「구조화 UI가 적합한 영역」과 「중요한 판단을 모두 채팅으로 처리하지 않는다」는 1.2 그대로 유효하며, 오히려 더 강하게 지켜진다.

### 대화 대신 무엇으로 하는가

| 1.2에서 대화로 하려던 것 | 지금 |
| --- | --- |
| AI가 잘못 이해한 내용 수정 | 결과 페이지에서 문제 항목 수정·다른 후보 선택·재탐색 |
| 「조금 전이었어」 같은 자연어 보정 | §9 `조금 전이에요` / `조금 후예요` 버튼 |
| 분석 진행상황 설명 | §7 작업 목록 + 시간축 + 경과시간 |
| 결과가 없거나 실패했을 때 다음 행동 안내 | §22·§23 전용 화면과 출구 버튼 |

### 구조화 UI가 적합한 영역

* 상위 후보 비교
* 사건 근거
* 번호판 이미지
* 발생시각과 출처
* 위치 단서
* 신고유형
* 신고요건
* 최종 신고자료

중요한 판단을 모두 채팅으로 처리하지 않는다.

# 3. 정보 상태와 작업 상태

정보의 신뢰 상태와 AI 작업 진행 상태는 서로 구분한다.

## 3-1. 정보 상태

번호판·발생시각·위치 등 중요한 값에는 가능한 경우 **값 + 출처 + 상태**를 함께 표시한다.

### AI 추정

AI가 영상 또는 사용자 단서를 바탕으로 추론한 값.

### 출처 확인됨

영상 화면, 파일 메타데이터, GPS 등 확인 가능한 출처에서 얻은 값.

### 사용자 확인됨

사용자가 직접 보고 확인하거나 수정한 값.

### 확인 필요

일부 정보가 불확실하여 사용자의 확인이 필요한 값.

### 알 수 없음(UNKNOWN)

신뢰할 만한 근거가 없어 값을 확정하지 않는 상태.

`AI 인식`, `사용자 확인 필요` 등 별도의 유사 상태 표현을 추가하지 않고 위 상태를 일관되게 사용한다.

## 3-2. 작업 상태

AI 분석 진행은 별도로 표현한다.

```text
완료
진행 중
대기
부분 완료
중단
실패
```

정보의 신뢰도와 작업 진행 여부를 같은 표시 체계로 섞지 않는다.

# 4. 전체 핵심 흐름

```text
홈 — 블랙박스 영상 올리기 + 상황 설명
        ↓
영상에서 읽은 정보와 사용자 기억 단서를 함께 받음
        ↓
AI가 시간 / 차량 / 상황 / 위치 단서를 구조화
        ↓
AI 분석 시작
        ↓
진행상황과 현재 탐색 범위 표시
        ↓
사건 후보 탐색·비교·검증
        ↓
결과 상태에 따라 분기
        │
        ├─ 후보 하나 이상
        │      → 가장 유력한 후보 기준으로 신고자료 초안 준비
        │
        ├─ 정보 부족
        │      → 필요한 단서만 추가 질문
        │
        ├─ 유사 후보만 있음
        │      → 부분 결과 + 범위 조정
        │
        └─ 실제 분석 실패
               → 복구 / 재시도
        ↓
AI가 후보 장면에 종속된 정보를 자동 준비
(사건 구간 · 번호판 · 발생시각 · 위치 — 신고 상황 응답과 무관한 작업)
        ↓
결과 화면 — 확보된 값을 상태·출처와 함께 표시
        ↓
결과 화면에서 신고 상황 응답 · 필요한 정보만 수정
        ↓
신고요건 검사
        ↓
신고자료 묶음 생성 (신고문 · 신고용 영상)
        ↓
신고자료 최종 확인 · 사용자 최종 검토
        ↓
안전신문고 제출 단계로 연결
        ↓
실제 제출은 사용자
```

기본 흐름은 **계약으로 가장 유력하다고 판단된 후보를 기준으로 초안을 준비하고, 결과 화면에서 사용자가 전체 신고자료를 검토하는 것**이다. 후보 순위가 없거나 최신 후보가 아니면 가장 유력한 후보를 임의로 정하지 않고, 결과 준비를 시작할 수 없다(§8).

**결과 화면을 보여 줄 수 있는 시점과 신고자료 묶음이 완성되는 시점은 같지 않다**(#171 C). 결과 화면은 신고자료 묶음 전에도 열리고, 그때까지 확보된 값을 보여 준다. 신고자료 묶음은 사용자가 결과 화면에서 신고 상황에 실제로 응답한 뒤에만 만들어지며(§15), 안전신문고 제출 단계로의 연결은 묶음이 만들어진 뒤에만 가능하다(§20). 계약상 이름은 `READY` = `PACKAGE_READY`이다(`architecture/contracts/contract-job-record-case-view.md` B절).

`[프로토타입]` **「정보 부족 → 필요한 단서만 추가 질문」 분기는 만들지 않았다.** 단서가 부족하면 되묻지 않고 그대로 탐색한 뒤, 결과가 없을 때 §22의 출구를 준다. 되묻는 편이 나은지는 사용자 평가에서 확인한다.

## 4-1. 진행 단계 표시

`[프로토타입]` 사용자에게는 아래 **3개 큰 단계**로 보인다. 세부 확인과 보정은 각 단계 안에서 이어지며, 처음부터 별도 홈·새 신고 화면을 거치지 않는다.

| 단계 | 사용자가 하는 일 | 이 문서의 절 |
| --- | --- | --- |
| 1 홈 — 영상 올리기 | 블랙박스 파일을 올리고 기억나는 상황을 적는다 | §5 |
| 2 영상에서 사건 찾기 | AI가 단서와 탐색 범위를 구성하고, 후보를 찾은 뒤 가장 유력한 후보 기준으로 자료가 준비되는 과정을 본다 | §6–§9 · §22 · §23 |
| 3 신고자료 확인 | 준비된 결과를 보고 신고 상황에 응답하고, 필요한 항목만 수정하거나 다른 후보로 바꾼 뒤, 신고자료 묶음이 완성되면 안전신문고 제출 단계로 넘긴다 | §10–§21 |

**후보 없음·분석 실패도 2단계 안의 결과로 표시한다.** 실패는 다른 단계가 아니라 같은 단계의 다른 결과다. 이 표시는 **읽기 전용이며, 눌러서 이동하지 않는다.**

## 4-2. 구현용 화면 전환 원칙

이 표는 화면이 어떤 값을 보고 어느 행동을 보낼지 정리한 제품 수준 경계다. 세부 API·payload는 `case`와 `web` 계약이 소유하되, 화면이 AI 판단을 재계산하거나 사용자 행동을 임의의 재발주로 바꾸지 않는 기준으로 쓴다.

| 제품 단계 | 들어오는 조건 | 사용자가 하는 행동 | 다음 상태 | 반드시 보존할 것 |
| --- | --- | --- | --- | --- |
| 1 홈 — 입력 | 첫 화면 진입 | 영상·상황 설명 제출 또는 빈 설명으로 진행 | 2 사건 찾기 | 원본 파일, 설명 원문, 구조화 전 단서 |
| 2 사건 찾기 — 분석 진행 | 영상·상황 입력이 제출됨 | 진행 관찰 / 중단 | 2 가장 유력한 후보 초안 준비 또는 2의 결과 없음·실패 | 구조화 단서, 우선 범위, 이미 찾은 후보와 완료된 작업 |
| 2 사건 찾기 — 가장 유력한 후보 초안 준비 | 순위가 보장된 최신 후보가 하나 이상 있음 | 진행 관찰 / 중단 | 3 신고자료 확인 | 후보 목록, 선택된 후보 식별자, 현재 초안 |
| 3 신고자료 확인 — 정보 | 가장 유력한 후보의 후속 자료가 준비됨 | 문제가 있는 값 수정 / 다른 후보 선택 / 결과 근거 보기 | 3 신고자료 또는 2 새 후보 초안 준비 | 현재 초안, 사용자 수정 값과 출처 |
| 3 신고자료 확인 — 자료 | 신고요건과 자료 상태가 표시됨 | 최종 검토 / 문제 항목 수정 / 다른 후보 선택 | handoff(신고자료 묶음이 있을 때만) 또는 해당 정보 확인 화면 | 원본·파생영상 구분, 수정 이력, 불확실성 표시 |

다음 전환은 특히 섞지 않는다.

* **다른 후보 선택**은 결과 화면에서 시작하는 **새 선택(selection context)과 새 신고자료 초안** 요청이다. 선택한 후보와 다시 확인할 정보를 표시한 뒤 새 초안을 준비한다. 이전 후보의 값은 승계하지 않는다(§9). 결과 재사용·이력·연속 선택 처리는 현재 범위 밖이다(§27).
* **조건 수정·시간 보정·전체 거절**은 새 탐색 의도다. 기존 후보와 초안을 데이터에서 지우지 않고 새 분석을 시작하며, 어떤 범위가 바뀌는지 먼저 고지한다. 이전 탐색의 후보는 기록으로 남지만 새 탐색 결과와 섞어 순위를 매기지 않고, 결과 화면에는 새 탐색의 후보만 보인다. 이전 신고자료 묶음으로 제출 단계에 넘어가지 않는다(#170 F).
* **값 수정**은 같은 선택 안에서의 사건 정보 보정이다. 필요한 후속 작업만 다시 수행하며, 무관한 사용자 확인 값을 초기화하지 않는다.
* **분석 중단·timeout·인프라 실패**는 사건 선택 단계로 가는 다른 결과다. 실패 화면을 별도 여정으로 만들지 않고, 보존된 결과와 다음 행동을 같은 맥락에 둔다.

# 5. 홈: 영상 업로드와 기억 단서 입력

홈은 별도 안내·새 신고 선택 화면이 아니라, **영상 업로드와 상황 설명을 한 번에 시작하는 화면**이다. 사용자는 여러 블랙박스 파일을 올리고 기억나는 단서를 자유롭게 적은 뒤 분석을 시작한다.

`[프로토타입]` 업로드가 끝나면 **영상에서 읽은 것을 이 흐름 안에서 보여준다** — 촬영 시간, 화면에 시각이 찍혀 있는지, GPS 기록이 있는지. **GPS가 없다는 사실은 여기서 말한다.** 마지막 handoff(§21)에서 처음 알게 해서는 안 된다.

`[프로토타입]` **「화면에 시각이 없다」와 「확인하지 못했다」는 다른 말이다.** 앞은 사실이므로 그대로 적고(그러면 파일 기록으로 계산한다 — §13), 뒤는 §3-1의 `알 수 없음(UNKNOWN)`으로 적는다. **둘을 하나로 합쳐 「없음」이라고 쓰지 않는다** — 없다고 하면 사용자는 화면을 다시 보지 않는다. 이 시점에 읽는 것은 **표시가 있는지 없는지뿐이고 시각 값은 읽지 않는다**(`architecture/module-architecture.md` §7-1). 둘을 구분하는 판정 기준은 `readout` Technical Spec의 미결 항목이다. 읽을 수 없는 파일은 건너뛰되 건너뛴 사실을 보여주고, 전체를 중단시키지 않는다(§23).

그리고 현재 서비스 범위를 짧게 안내한다.

```text
대신고는 블랙박스 영상에서
신고할 가능성이 있는 사건을 찾아드립니다.

현재 지원
• 신호위반
• 중앙선 침범
• 진로변경
• 이륜차 안전모 미착용

AI가 보여주는 결과는 법적 위반 확정이 아니라
신고할 가능성이 있는 사건 후보입니다.

실제 사건과 주요 신고정보는
제출 전에 직접 확인해주세요.
```

이후 사용자는 자연어로 상황을 설명한다.

```text
무슨 일이 있었는지
기억나는 만큼 말씀해주세요.

예)
시간     6시 반쯤 / 퇴근길 7시 전후
상황     빨간불인데 직진 / 실선을 넘어 끼어듦
차량     흰색 SUV / 검은 승용차 / 오토바이
위치     미금역 근처 / ○○IC 지난 뒤
```

사용자:

> “6시 반쯤 흰 SUV가 실선을 넘어 끼어들었어요. 미금역 근처였던 것 같아요.”

필수 정보를 모두 정확하게 기억할 필요는 없다.

`[프로토타입]` 여기에 두 가지 규칙을 더한다.

* **입력 중에 실시간으로 파싱 결과를 보여주지 않는다.** 문장이 끝나기 전의 틀린 해석은 도움이 아니라 방해다. 구조화 결과는 제출 후 §6에서 한 번에 보여준다.
* **빈 입력을 막지 않는다.** 「시간 단서 없이 전체 찾기」로 안내하고 그대로 진행한다.

# 6. AI의 이해와 탐색 범위 구성

사용자가 영상과 상황을 제출하면 AI가 시간·차량·상황·위치 단서를 구조화하고 우선 탐색 범위를 구성한 뒤 바로 분석을 시작한다. 사용자는 이 내부 계획을 중간에 승인하거나 수정하지 않는다.

우선 탐색 범위는 나머지 영상을 버린다는 뜻이 아니다. 다만 남은 범위를 더 확인하는 것은 아래 「한 번의 탐색이 하는 일」대로 **사용자 행동으로 시작하는 새 탐색**이다. AI가 스스로 범위를 넓혀 이어서 탐색하지 않는다.

AI가 어떤 단서와 범위를 사용했는지는 사용자가 **궁금할 때만** 결과 화면의 `어떻게 정했는지`에서 볼 수 있다. 잘못 이해했거나 결과가 맞지 않을 때의 수정은 결과 화면에서 값 수정·다른 후보 선택·재탐색으로 시작한다.

### 한 번의 탐색이 하는 일

원칙(#170 F): 처음 위임한 탐색 범위·예산 **안의** 후속 확인은 자동으로 할 수 있고, 이를 넘는 확대(시간 범위 확대·조건 수정·영상 전체 재탐색)는 **새 사용자 탐색 의도**다.

현재 범위에서는 위임 범위 안의 자동 후속 **탐색**도 없다. 자동 후속 탐색 기능과 비용 상한 집행이 아직 없기 때문이다.

* 한 번의 탐색 의도는 **후보 탐색 + 가장 유력한 후보 1개의 상세 확인**으로 끝난다.
* 후보 탐색은 일반 영상이면 **한 번**이다. 한 번에 처리할 수 있는 길이를 넘는 긴 영상은 여러 구간(클립)으로 나눠 탐색할 수 있고, 이때 성공한 구간 결과를 모은 것이 그 탐색의 결과 하나다(#168). 클립 분할은 아직 구현되지 않았다.
* 가장 유력한 후보의 상세 확인에서 위반이 관찰되지 않으면, 음성 결과와 `다른 후보 보기`로 끝난다. **다음 후보를 자동으로 확인하지 않는다**(#168 [A]). 다른 후보의 상세 확인은 사용자가 그 후보를 고를 때만 한다.
* 탐색 비용은 사용자 행동(새 탐색, 다른 후보 선택)에만 묶여 늘어난다. 제품이 스스로 탐색을 반복하지 않는다.
* 번호판·화면 시각 재판독처럼 이미 고른 후보를 다시 관찰하는 작업은 탐색 확대가 아니므로 이 제한과 별개다.

위임 범위 안의 자동 후속 탐색(예: 가장 유력한 후보가 기각되면 다음 후보를 자동 확인)이 생기면 그때 위 원칙을 적용해 범위를 정한다.

# 7. AI 분석 진행

분석 중에는 로딩 화면만 보여주지 않는다.

```text
사건을 찾고 있어요.

✓ 우선 확인 범위 구성
  42개 중 9개 파일

● 사건 가능성이 있는 장면 확인 중
  9개 중 4개 파일 확인

○ 후보 장면 비교

경과시간 01:42
```

필요하면 중간 결과를 설명한다.

```text
현재까지 흰색 SUV가 등장하는
후보 장면 5개를 찾았습니다.

실선과 차량 이동을 추가로 확인하고 있습니다.
```

충분한 실측 데이터가 확보되기 전에는 부정확한 남은 시간(ETA)을 임의로 표시하지 않는다.

`[프로토타입]` **진행률 퍼센트도 표시하지 않는다.** ETA를 금지한 것과 같은 이유다 — 뒤로 갈수록 느려지는 작업에서 퍼센트는 남은 시간을 잘못 약속한다. 보여줄 것은 셋이다.

```text
시간축이 확인되어 가는 모습
영상 9개 중 4개 확인
경과시간 01:42
```

후보는 **도착하는 대로** 목록에 쌓인다. 끝날 때까지 아무것도 보여주지 않는 화면이 아니다.

사용자는 분석 중 다음 행동을 할 수 있다.

```text
[찾는 조건 수정]
[분석 중단]
```

### 사용자가 분석을 중단한 경우

현재까지 얻은 결과를 버리지 않는다.

```text
분석을 중단했습니다.

현재까지 사건 후보 3개를 찾았습니다.

[현재 후보 보기]
[이어서 찾기]
[조건 수정]
```

`[프로토타입]` **중단은 확인 대화 없이 즉시 실행한다.** 멈추겠다는 사람을 붙잡지 않는다. 곧바로 후보 화면(§8)으로 가되 상단에 **부분 결과임을 밝히고** `이어서 찾기`를 함께 둔다. 「조건 수정」으로 §6에 돌아가는 경우에도 **이미 찾은 후보를 버리지 않는다.**

**현재 범위(#168 결정 3 · #170 F).** `이어서 찾기`는 안 본 구간만 이어서 보는 동작이 아니라 **영상 전체를 다시 보는 새 탐색 의도**다. 새 탐색의 후보는 이전 탐색의 후보와 섞지 않는다(§4-2). 탐색 도중 중단되거나 시간 제한에 걸린 탐색은 지금은 보존할 부분 후보를 남기지 않는다 — 위 「현재까지 후보 3개」 같은 부분 결과는 구간 단위 부분 결과가 생긴 뒤의 동작이다. 실패를 「후보 없음」으로 보여 주지 않는다(§23).

# 8. 사건 후보 결과

## 8-1. 가장 유력한 후보로 초안을 먼저 준비한다

후보를 찾으면 제품은 최신 후보 중 **계약으로 가장 유력하다고 판단된 후보**를 선택해 `신고자료 초안 준비`로 바로 넘어간다. 이는 법적 판단이나 실제 신고의 자동 승인이 아니다. 사용자가 중간에 후보·번호판을 따로 통과시키지 않아도 되도록, AI가 사건 구간·번호판·시각·위치 단서·위반 내용·신고용 영상을 한 묶음으로 준비하는 기준이다.

```text
후보 3개를 찾음
        ↓
가장 유력한 후보 기준으로 신고자료 준비 중
        ↓
번호판 · 화면 시각 · 위치 단서 · 위반 내용 · 신고용 영상 확인
        ↓
신고자료 결과 화면
```

진행 화면은 사용자를 멈춰 세우는 확인 화면이 아니다. 이미 끝난 업로드·탐색·후보 선택은 **짧은 초록색 완료 표시**로 계속 보이고, 새 후보에 종속된 정보를 다시 읽는 과정부터 이어 보여 준다. 사용자가 앞선 작업을 하지 않았다고 오해하지 않게 하기 위해서다. 번호판이나 위치가 불확실해도 여기서 사용자 행동을 요구하지 않고, 결과 화면의 `확인 필요` 항목으로 넘긴다.

가장 유력한 후보는 **현재 탐색 의도의 결과**에서 search가 준 순서의 첫 후보다. case는 그 순서대로 후보를 받아 첫 후보를 자동 선택한다. 후보가 0개이면 기존의 `후보 없음` 결과로 안내한다. web은 순위나 중복을 계산하지 않고, 후보를 자동 선택하지 않는다.

* 일반 영상은 탐색 한 번의 결과이므로, 그 탐색이 준 `rank=1` 후보가 가장 유력한 후보다.
* 긴 영상을 여러 구간으로 나눠 탐색한 경우(§6)는 성공한 구간 결과를 **하나의 후보 묶음**으로 보고, 그 묶음을 search가 정한 기준으로 줄 세운 첫 후보가 가장 유력한 후보다. 줄 세우는 기준은 search·case 계약이 정한다(`architecture/contracts/contract-analysis-run-candidate-event.md` §6-2, `contract-job-record-case-view.md` B절 §7).
* 이전 탐색 의도의 후보와 현재 탐색의 후보를 섞어 새 순위를 만들지 않는다(§4-2).
* 과거 영상 기준(stale)의 후보는 자동 선택하지 않는다.
* 가장 유력한 후보에서 위반이 관찰되지 않으면 음성 결과와 `다른 후보 보기`로 끝나고, 다음 후보를 자동으로 확인하지 않는다(§6).

### 결과 화면에서 다른 후보를 선택할 수 있다

결과 화면에는 **신고용 영상**과 함께 다른 후보를 보는 선택적 출구를 둔다. 사건 영상을 별도 화면으로 두지 않는다 — 다만 신고 상황 응답 옆에는 그 판단의 근거가 되는 사건 장면을 함께 둔다(§15, #171 B-2). 사용자는 기본적으로 결과만 검토하고, 현재 결과가 아니라고 판단할 때만 후보 비교를 연다. `어떻게 정했는지`는 궁금할 때만 여는 선택적 근거 보기다.

다른 후보를 선택하면 제품은 다음을 한다.

1. `새 후보 기준으로 신고자료를 다시 준비 중`임을 알리고 진행 화면으로 이동한다.
2. 새 후보에 종속된 번호판·시각·위치·위반 내용·신고용 영상·요건을 다시 확인한다.
3. 새 선택 기준의 결과 화면을 보여 준다.

새 후보를 준비하는 동안에는 다시 후보를 바꾸는 동작을 제공하지 않는다. 준비가 끝난 뒤 결과 화면에서 다음 후보를 고를 수 있다.

새 후보 선택은 기존 결과에 대한 단순 UI 전환이 아니라, **새 선택(selection context)과 새 신고자료 초안을 만드는 작업**이다(#173 E-1). 이전 후보의 값은 새 후보로 자동 이월하지 않는다 — 무엇을 새로 준비하는지는 §9 「다른 후보를 선택한 경우」가 정한다.

신고자료 묶음이 이미 만들어진 결과에서도 다른 후보를 고를 수 있다(#173 E-4). 고르는 순간 현재 결과는 새 초안 준비 상태로 돌아가고, **이전 후보의 신고자료 묶음으로는 제출 단계에 넘어가지 않는다.** 이전 후보를 위해 시작된 작업의 결과가 늦게 도착해도 새 초안에 쓰지 않는다.

---

## 8-2. 비교 화면의 정보와 출구

비교 화면은 결과에 대한 선택적 보정 출구다. Top-3까지 각각 다음을 제공한다.

* 원본 영상과 사건 구간
* 영상에서 읽은 시각(있을 때만)과 시간축 위치
* AI가 관찰한 사건 내용과 불확실성(제공될 때만)
* 사용자가 입력한 기억 단서
* 이 후보로 새 초안을 만들기, 시간 보정, 전체 거절의 출구

후보 카드의 번호는 시간축 마커의 번호와 같아야 한다. 시간·차량·상황이 어긋나는지는 화면이 추론하지 않는다. 상류가 관찰 근거나 불확실성을 제공하면 맞는 내용뿐 아니라 불리한 근거도 같은 위계로 표시한다. 그렇지 않으면 사용자가 원본과 두 문장을 직접 비교한다.

# 9. 사용자 보정

사용자가 AI 결과를 수정해도 가능한 경우 전체 작업을 처음부터 다시 하지 않는다.

`[프로토타입]` 보정은 **자연어가 아니라 버튼으로 받는다**(§2). 1.2가 예로 들던 「이 차는 맞는데 조금 전이었어」는 `조금 전이에요` 버튼 하나에 대응한다. 무엇이 유지되고 무엇이 바뀌는지를 제품이 보장해야 하는데, 자유 문장으로는 그 범위를 확정할 수 없기 때문이다.

`조금 전이에요` 를 누르면:

```text
같은 차량을 기준으로
이전 구간을 다시 확인할게요.

유지
차량: 흰색 SUV
상황: 실선 침범

변경
시간 범위: 이전 2분
```

```text
18:29:48 ~ 18:31:48을 다시 확인하고 있습니다.
```

여기서 「유지」는 **탐색 조건(사용자 기억 단서)** 을 유지한다는 뜻이다. 시간 보정은 새 탐색 의도이므로(§4-2) 재탐색 뒤 고르는 후보는 새 선택이며, 그 후보의 번호판·신고 상황은 아래 「다른 후보를 선택한 경우」대로 새로 준비한다(#173 E-3).

### 사건 안에서 수정하는 정보

* 번호판
* 발생시각 관련 단서
* 위치 단서
* 신고 상황 설명

### 다시 탐색이 필요한 수정

* 시간 범위 변경
* 차량 특징 변경
* 다른 사건 요청

다시 탐색이 필요한 경우 사용자가 추가 분석이 발생함을 알 수 있게 한다.

### 불필요한 재확인 금지

**같은 선택 안에서는 한 번 `사용자 확인됨`이 된 값을 다시 묻지 않는다.** 「같은 선택」은 같은 후보를 기준으로 한 하나의 신고자료 초안(selection context)이다.

* §20 최종 확인에서 §10으로 되돌아와도 상태를 유지한다.
* 같은 선택 안에서 다른 값을 수정하거나 시각만 다시 해석해도, 번호판·신고 상황처럼 그 수정과 무관한 확인 값은 초기화하지 않는다.

**다른 후보를 선택한 경우는 같은 선택이 아니다**(#173 E-1 · E-3). 새 선택의 새 초안이므로 후보에 종속된 값을 새 후보 기준으로 준비하고, 이전 후보의 값을 자동 승계하지 않는다. 시간 보정으로 재탐색한 뒤 고른 후보도 여기에 해당한다 — 같은 차량이라는 보장이 없기 때문이다.

| 후보에 종속된 값 | 다른 후보를 선택하면 |
| --- | --- |
| 번호판 | 새 사건 구간에서 다시 판독한다. 사용자가 이전 후보에 직접 입력한 번호판도 새 후보의 `사용자 확인됨`이 되지 않는다 |
| 발생시각 | 새 사건 시점의 근거로 다시 정한다 |
| 위치 | 새 후보 기준으로 다시 정리한다 |
| 사건 구간 · 신고용 영상 | 새 후보로 다시 만든다 |
| 위반 내용 · 신고 상황 응답 | 새 후보에 대한 새 응답을 받는다. 이전 응답을 복사하지 않는다 |
| 최종 검토(`USER_REVIEWED`) | 이전 결과에 대한 검토를 새 초안의 검토로 쓰지 않는다 |

사용자가 처음 입력한 기억 단서는 후보가 아니라 사건 전체에 걸린 값이라 후보를 바꿔도 유지된다.

AI는 새 사건 구간을 기준으로 다시 읽고, 진행 화면에는 재확인 과정을, 결과 화면에는 새 값과 상태·출처를 보여 준다. 이전 입력을 참고로 보여 주는 것과 「이 후보에도 적용」하는 동작은 이번 범위에 넣지 않는다 — 옛 값만 보이면 사용자가 새 후보에도 들어갔다고 읽기 쉽다. 재입력 부담이 실제로 관찰되면 후속으로 검토하며, 그때도 새 후보의 값으로 자동 승격하지 않고 사용자가 새로 적용한 입력으로 기록한다(#173 E-2).

같은 것을 두 번 묻는 것은 사용자가 이 제품을 신뢰하지 않게 되는 가장 빠른 길이다. 다만 다른 후보에 대해 다시 묻는 것은 같은 것을 두 번 묻는 것이 아니다.

> `[프로토타입]` 프로토타입은 후보를 바꿔도 번호판을 유지한다(`design/PROTOTYPE-SPEC.md` §4.3). 흐름 검증용 동작이며 제품 정책이 아니다(#173).

# 10. 가장 유력한 후보 기준 신고자료 준비

가장 유력한 후보가 정해지면 사용자가 새로운 메뉴를 직접 찾아다니지 않는다. AI가 후속 작업을 이어서 수행하고, 진행 중에 번호판·신고 상황을 따로 승인받지 않는다.

```text
이 사건을 신고할 준비를 하고 있습니다.

✓ 사건 구간 구성
● 차량번호 확인
● 발생시각 확인
● 위치 정보 확인
● 신고 상황 정리
○ 신고용 영상 생성
○ 신고요건 검사
```

**신고 상황 응답 전에 어디까지 하는가**(#171 B). 사건 구간 구성·번호판 판독·화면 시각 판독·발생시각 계산처럼 **신고 상황 응답과 무관한 작업**은 응답을 기다리지 않고 진행해, 결과 화면에 부분 결과로 보여 준다. 신고문과 신고자료 묶음처럼 신고 상황에 따라 달라지는 최종 자료는 **사용자가 결과 화면에서 신고 상황에 실제로 응답한 뒤**에만 완성한다(§15). 응답 전에 만든 관찰 결과는 버리지 않고, 응답 뒤 같은 선택 안에서 그대로 다시 쓴다. 가장 유력한 후보에서 위반이 관찰되지 않은 경우(§6)는 이 선행 작업을 하지 않는다.

여러 항목에서 사용자 확인이 필요한 경우:

```text
확인할 항목 2개

1. 차량번호
2. 신고 상황
```

처럼 현재 남은 판단 수를 보여준다.

# 12. 번호판

## 번호판을 판독한 경우

```text
차량번호

12가 3456

출처
영상에서 가장 선명한 번호판 장면과
주변 장면을 함께 확인

상태
AI 추정

[번호판 이미지 보기]
[맞아요]
[수정]
```

사용자가 `[맞아요]`를 누르거나 직접 수정한 이후에만:

```text
상태
사용자 확인됨
```

으로 바뀐다.

## 일부 문자가 불확실한 경우

```text
차량번호 확인이 필요해요.

[번호판 확대 이미지]

AI 추정
12가 34?6

5번째 문자를 확실하게 읽지 못했습니다.

상태
확인 필요

[다른 장면 보기]
[확대]
[직접 입력]
```

전혀 판독할 수 없는 경우 값을 만들지 않는다.

```text
차량번호
알 수 없음

상태
UNKNOWN
```

**번호판을 읽지 못한 것 자체는 신고자료를 막지 않는다**(#146 방향 · #172 D·D-3 결정). 값은 만들지 않고 비워 두며(「UNKNOWN」 같은 문자를 차량번호로 넣지 않는다), 부족한 정보임을 경고와 함께 표시한 채 결과까지 준비한다. `[프로토타입]` `읽을 수 없음`으로 둬도 **경고 대화 없이 끝까지 진행된다.** 번호 없이 만든 자료도 자료다.

다음 셋은 같은 「알 수 없음」처럼 보여도 서로 다른 상태로 다룬다.

| 상태 | 사용자에게 | 신고자료 |
| --- | --- | --- |
| 판독은 했지만 번호를 읽지 못함 · 일부만 읽음 | `알 수 없음` 또는 `확인 필요`, 값은 비움 | 경고로 두고 막지 않는다 |
| 최종 신고용 영상에서 번호판이 보이는지 | MVP에서는 확인하지 않는다. 「보인다」고도 「안 보인다」고도 말하지 않는다 | 막지 않는다 — 완성된 신고용 영상을 다시 판독하는 단계가 없다(#280) |
| 번호판 판독 **실행 자체가 실패함** | 판독에 실패했음과 `다시 판독` 출구(§23) | 「읽지 못함」 결과로 바꿔 넘기지 않는다. 실패한 채로 신고자료를 완성하지 않는다 |

판독은 했지만 번호를 읽지 못한 채 만든 신고문에는 차량번호 자리를 두지 않고, **차량번호를 영상에서 식별하지 못했다는 사실을 한 문장으로 밝힌다.** 번호를 지어내거나 「UNKNOWN」을 적지 않는다. 문구는 `modules/evidence/decisions/safety-report-policy-v1.2.md`가 소유한다.

사건 구간에서 읽은 결과만으로 최종 신고용 영상에서 번호판이 보인다고 판정하지 않는다. MVP는 완성된 신고용 영상을 다시 판독하지 않으므로(#280) 그 영상에서의 번호판·화면 시각 가시성은 판정하지 않는다 — 신고용 영상은 결과 화면에서 사용자가 직접 볼 수 있고(`[신고용 영상 보기]`), 번호판 근거는 선택 첨부인 번호판 이미지로 보탠다. 번호판 이미지를 만들지 못해도 신고자료를 막지 않는다. 상태별 요건 판정 규칙은 `modules/evidence/adr/adr-plate-identification-failure-boundary.md`(ADR-EVIDENCE-008)와 `modules/evidence/adr/adr-i4-report-video-visibility-rules-removal.md`(ADR-EVIDENCE-010)가 소유한다.

## `[프로토타입]` 「맞아요」 버튼을 만들지 않는다

`12가 34?6`처럼 **물음표가 든 값을 「맞다」고 확인할 방법이 사용자에게 없다.** 그래서 불확실한 번호판에 확인 버튼을 두지 않고, 선택지를 둘로만 준다.

```text
[번호 직접 입력]
[읽을 수 없음으로 두기]
```

선명하게 판독된 경우에도 같은 선택지를 유지했다. 「맞아요」 하나로 확정 상태를 만들면 사용자가 실제로 대조하지 않고 누르게 되고, 그 값은 `사용자 확인됨`이라는 이름만 얻는다. 1.2 §12의 판독한 경우에 있던 `[맞아요]`는 이 이유로 뺐다.

## `[프로토타입]` 번호판 장면 넘겨보기

한 장면만 보여주고 판단을 요구하지 않는다. 여러 장면을 넘겨보게 하고, **각 장면이 왜 잘 안 보이는지 함께 말한다.**

```text
선명 · 흔들림 · 반사 · 가림

2번은 흔들렸고, 3번은 빛이 반사됐고, 4번은 뒷차에 가렸습니다.
```

「안 보인다」와 「왜 안 보이는지」는 다르다. 뒤쪽만이 사용자가 다음에 무엇을 할지 정할 수 있게 한다.

## `[확정]` 차량번호 표기 규칙

| 층 | 규칙 |
| --- | --- |
| 입력 | `12가3456`과 `12가 3456`을 **모두 받는다** |
| 내부 처리 | 비교·검증할 때만 공백을 지운다 |
| 표시 | 확정된 값을 **그대로** 보여준다. 임의로 공백을 넣거나 빼지 않는다 |
| 안내 문구 | 「띄어쓰기 없이 입력」류 문구를 **넣지 않는다** |

형식이 어긋나도 **저장을 막지 않는다.** 지역·구형 번호판 등 예외가 있고, 최종 판단은 사용자와 접수기관의 몫이다. 형식이 이상하면 경고만 한다.

이 항목은 확정됐다. §26 미결에서 제외한다.

## 파일 기록을 이용해 계산한 경우

```text
발생시각 후보

2026-08-24 18:31:48

출처
원본 파일에 기록된 촬영 시각과
영상 내 사건 위치를 기준으로 계산

주의
영상 화면에 원래 표시된 시각은 아닙니다.

상태
확인 필요
```

## 파일 기록끼리 시각이 다른 경우

```text
발생시각 후보

2026-08-24 18:31:48

출처
원본 파일명에 기록된 시각 기준

주의
파일 메타데이터의 시각과 다릅니다.

상태
확인 필요
```

값을 비우지 않는다. 파일명 시각을 기본값으로 쓰고 **충돌 사실을 함께 보여준다.** 어느 기록이 맞는지 사용자에게 고르게 하는 별도 단계를 두지 않으며, §20 최종 확인에서 수정할 수 있다. 어느 기록을 기본값으로 삼는지는 `architecture/module-architecture.md` §3-2가 정한다.

사용자가 실제로 검증할 방법이 없는 정보에 억지로 “확인” 버튼을 요구하지 않는다.

필요하면 안전신문고 제출 시 참고해야 할 정보로 고지한다.

# 15. 신고 상황 확인

AI는 법률적 최종 판정을 요구하지 않는다.

대신 영상에서 관찰한 상황을 사용자에게 확인시킨다.

```text
이 사건을 이렇게 정리했습니다.

"흰색 SUV가 백색 실선을 넘어
인접 차로로 변경한 상황"

근거
• 백색 실선 확인
• 차량이 선을 넘어 이동
• 인접 차로 진입

상태
AI 추정

[맞아요]
[다른 상황]
[잘 모르겠어요]
```

사용자가 전문적인 법적 유형을 직접 판정하도록 요구하지 않는다.

구체적인 신고유형 매핑은 신고 규칙을 기반으로 별도로 처리한다.

`[프로토타입]` **`잘 모르겠어요`도 진행을 막지 않는다.** 값은 `AI 추정`으로 남고 §20 최종 확인에 그렇게 표시된다. 모르겠다는 대답에 벌을 주면 사용자는 다음부터 아무거나 누른다.

### 언제 묻고, 무엇으로 기록하는가

결정: #171 B-2.

* **결과 화면의 「신고 상황」 항목에서 묻는다.** 진행 화면(§10·§19)에서는 묻지 않는다. 사용자가 `[맞아요]`·`[다른 상황]`·`[잘 모르겠어요]`를 **실제로 누른 시점**에 응답을 기록한다.
* 「신고 상황」은 AI가 위반을 관찰한 결과를 포함해 **모든 결과에서 확인 필요 항목**으로 둔다. 응답 전에는 신고자료 묶음이 만들어지지 않는다(§4).
* **응답하지 않은 것은 「아직 묻지 않음」(`NOT_ASKED`)이다.** 시스템이 무응답을 `잘 모르겠어요`(`USER_UNSURE`)로 바꾸지 않는다. `잘 모르겠어요`는 사용자가 실제로 누른 응답일 때만 기록된다.
* 별도의 「이 사건 맞아요」 확인 단계를 다시 만들지 않는다. 대신 신고 상황 응답 옆에 그 판단의 근거가 되는 사건 장면을 두어 영상을 보고 응답하게 하고, 제출 단계로 넘어갈 때 최종 검토(§20)를 따로 기록한다.
* **신고 상황 응답과 최종 검토는 서로 다른 사용자 행동이다.** 한 번의 클릭으로 묶지 않는다.

# 16. 파일 경계 사건

사건이 두 블랙박스 파일 사이에 걸쳐 있더라도 하나의 사건으로 처리한다.

```text
이 사건은 두 영상 파일에 걸쳐 있습니다.

원본
FILE_001.mp4
FILE_002.mp4

신고용 사건 구간
18:31:52 ~ 18:32:09

[신고용 영상 보기]
[원본 파일 보기]
```

사용자에게는 하나의 연속된 사건 구간으로 보여주되, 어떤 원본 파일에서 만들어졌는지는 확인할 수 있게 한다.

구체적인 병합 방식(파일 경계 해석·이어진 사건 구간 생성)은 recording 모듈이 관리한다(`architecture/module-architecture.md` §3-3).

> `[프로토타입]` 이 절은 프로토타입에서 다루지 않았다. 흐름 검증용 mock 사건이 파일 하나 안에 들어 있었기 때문이며, **결정이 철회된 것이 아니다.** 실제 구현에서 처음 검증된다.

# 17. 원본과 신고용 파생영상 구분

대신고는 원본 블랙박스 파일을 수정하지 않는다.

```text
원본 영상
FILE_001.mp4
상태: 원본 유지

신고용 영상
daesingo_event_001.mp4
상태: 원본에서 생성된 파생영상
```

사용자가 다운로드하는 신고용 영상이 **원본이 아니라 파생영상**임을 명확히 표시한다.

원본과 파생영상의 실제 저장기간·삭제정책은 개인정보 및 운영 정책 문서에서 관리한다.

# 18. 신고요건 확인

AI는 신고자료 생성 전에 현재 신고 규칙을 기준으로 필요한 항목을 확인한다.

예:

```text
신고용 영상

20초
84MB / 허용 한도 130MB

상태
요건 충족
```

용량을 초과한 경우:

```text
신고용 영상의 용량이 허용 한도를 넘었습니다.

[영상 다시 압축]
[사건 구간 조정]
```

신고기한 역시 현재 신고 규칙을 기준으로 확인한다.

```text
신고기한
기한 내

또는

신고기한
확인 필요 / 기한 초과
```

규칙 값 자체는 Core User Flow가 아니라 신고 규칙 문서에서 관리한다.

# 19. 신고자료 준비 진행 상태

가장 유력한 후보 기준 신고자료를 준비하는 동안에는 결과 대신 **현재 어디까지 끝났는지 보여 주는 진행 화면**을 둔다. 사용자가 할 일은 없으며, 오래 걸릴 때 기다림의 이유를 알 수 있게 하는 화면이다.

```text
신고자료를 준비하고 있어요.

✓ 영상 12개를 받았어요
✓ 장면을 찾았어요
✓ 가장 유력한 후보를 골랐어요
● 번호판과 화면 시각을 같이 읽는 중이에요
○ 위치·위반 내용 정리
○ 신고용 영상과 신고문 만들기

경과시간 01:42
```

다른 후보를 고른 뒤에도 `영상 12개를 받았어요`·`장면을 찾았어요`·`새 후보를 골랐어요`는 초록색 완료 표시로 남기고, `번호판과 화면 시각을 같이 읽는 중이에요`부터 새로 진행한다. 이렇게 하면 사용자는 앞선 작업이 끝났고 새 후보 때문에 필요한 부분만 다시 읽는다는 것을 알 수 있다.

예상 완료시간·퍼센트는 제공하지 않는다. 실제 시간이 쌓이기 전에는 틀린 약속이 되기 쉽기 때문이다. 신고 상황 응답과 무관한 준비가 끝나면 §20 결과 페이지로 이동해 확보된 항목의 상태·출처를 보여 준다. 이때 신고 상황 응답 전이면 신고문·신고용 영상은 아직 없고, 결과 화면이 그 이유를 함께 보여 준다(§20 「신고자료 묶음 전」).

### 안전신문고에서 직접 확인할 항목

```text
• 최종 위치 핀 선택
```

GPS가 없어 제품 안에서 완료할 수 없는 정보를 `4/5` 같은 실패 상태로 표시하지 않는다.

## `[프로토타입]` 다음으로 넘어가는 조건

불확실한 값은 작업을 멈추게 하지 않는다. 번호판을 포함한 모든 값은 상태·출처와 함께 결과 화면으로 보내고, 사용자가 실제로 손봐야 하는 값만 `확인 필요`로 표시한다. `읽을 수 없음`도 결과를 만들 수 있다(§12). 사용자는 결과 화면에서 문제 항목을 열어 수정하거나, 필요하면 다른 후보를 고른다.

# 20. 신고자료 최종 확인

전체 정보를 다시 읽는 화면은 **여기 한 번만 제공한다.** 신고용 영상, 번호판, 시각, 위치, 위반 내용, 신고서 초안을 같은 결과로 보여 준다. 사건 영상은 별도 화면으로 제공하지 않고, 신고 상황 응답 옆의 근거 장면으로만 둔다(§15). 중간 단계의 후보 선택·번호판 확인은 이 화면을 만들기 위한 AI 작업이며, 사용자는 결과에서 필요한 항목만 연다.

**결과 화면은 하나이고, 신고자료 묶음 전과 후 두 상태를 가진다**(#171 C · C-2).

| 상태 | 보여 주는 것 | 제출 단계로 연결 |
| --- | --- | --- |
| **신고자료 묶음 전** | 확보된 값(번호판·발생시각·위치·위반 내용 등)과 각 값의 상태·출처 · 신고 상황 요약과 응답 버튼 · 사건 근거 장면(있으면) · 신고자료를 막는 항목과 다음 행동 · `다른 후보 보기`. 신고문·신고용 영상은 **자리를 두고, 왜 아직 없는지**(예: 신고 상황 응답 전)를 적는다 — 빈 칸으로 두지 않는다 | 비활성. 버튼 옆에 왜 아직 안 되는지 적는다 |
| **신고자료 묶음 후** | 아래 예시 전체 | 가능 |

묶음 전 상태에서 미완성 신고문이나 미완성 신고용 영상은 만들지 않는다. 값별 계약 필드와 이유 표시 방식은 `architecture/contracts/contract-job-record-case-view.md` B절이 정한다. AI가 신고 상황을 판단하지 못해 요약이 없는 경우의 부분 결과 표시는 CaseView 후속으로 따로 정한다(#171 C-2 후속).

```text
가장 유력한 후보 기준으로 신고자료를 준비했습니다.

사건
18:31:42 ~ 18:31:57

차량번호
12가 3456
상태: AI 추정 / 확인 필요 시 수정 가능

발생시각
2026-08-24 18:31:48
출처: 영상 화면에 표시된 시각

위치
미금역 사거리 인근
안전신문고에서 최종 위치 선택 필요

사건 설명
흰색 SUV가 백색 실선을 넘어
인접 차로로 이동한 상황

신고용 영상
20초 · 84MB
원본에서 생성된 파생영상
```

### 신고문

```text
[자동 작성된 신고문 전체 내용]

[신고문 수정]
```

사용자는 실제로 자신이 제출하게 될 신고문을 읽고 수정할 수 있어야 한다.

```text
[문제가 있는 항목 수정]
[다른 후보 보기]
[궁금할 때: 어떻게 정했는지]
```

`다른 후보 보기`를 고르면 §8-1의 새 초안 준비로 돌아간다. 새 결과가 준비되기 전까지는 새 후보의 값을 확정된 것처럼 표시하지 않는다. 신고자료 묶음 후 상태에서 골라도 같다 — 이전 후보의 묶음으로는 제출 단계에 넘어가지 않는다.

문제가 없으면 사용자는 이 화면에서 바로 안전신문고 제출 단계로 이동한다. 별도의 `신고자료 만들기` 또는 중간 승인 버튼은 두지 않는다. 제출 단계로의 연결은 **신고자료 묶음이 만들어진 뒤에만** 가능하고, 연결하는 순간을 사용자의 최종 검토(`USER_REVIEWED`)로 기록한다. 최종 검토는 신고 상황 응답과 별개의 행동이다(§15).

# 21. 안전신문고 제출 단계로 연결

최종 확인이 끝난 뒤 같은 정보를 다시 나열하지 않는다.

```text
신고자료가 준비되었습니다.

최종 위치는 안전신문고 지도에서 확인해주세요.

[신고용 영상 다운로드]
[신고내용 복사]
[안전신문고로 이동]
```

## `[프로토타입]` 붙여넣을 것과 직접 고를 것을 나눈다

**이 단계의 정확성이 제품 신뢰를 좌우한다.** 사용자가 실제 안전신문고 화면에서 헤매면 여기까지 아낀 시간이 전부 사라진다.

안전신문고의 입력칸은 성격이 두 가지인데, 그것을 화면이 먼저 갈라서 보여준다.

| 묶음 | 항목 | 표기 |
| --- | --- | --- |
| **붙여넣을 것** | 제목 · 차량번호 · 신고 내용 | 각각 복사 버튼. 전체 복사는 **칸 이름을 붙여** 복사한다 |
| **직접 고를 것** | 신고유형 · 발생일자 · 발생시각 · 발생장소 | **복사 버튼을 두지 않는다.** 각 항목에 어디를 눌러야 하는지 한 줄로 안내한다 |

**직접 고를 것에 복사 버튼을 두지 않는 이유:** 있으면 누르고, 왜 안 붙는지 헤맨다. 붙여넣을 수 없는 칸에 복사 버튼을 주는 것은 없는 기능을 약속하는 것이다.

**발생장소만 예외다** — 검색어를 복사해 지도 검색창에 붙여넣되, **핀은 안전신문고 지도에서 사용자가 놓는다**(§14). 자체 지도 UI는 MVP 범위가 아니다.

신고용 영상은 **파생영상**임을 표시해 내려받게 하고(§17), 안전신문고는 새 창으로 연다. 이 화면은 그대로 두고 옆에 놓고 볼 수 있어야 한다.

실제 신고 제출은 사용자가 직접 수행한다.

AI는 사용자 승인 없이 신고를 제출하지 않는다. **「접수」 버튼은 제품 어디에도 존재하지 않는다.**

# 22. AI 불확실성 대응

AI가 정상적으로 동작했지만 결과가 불확실한 상황과 시스템 자체가 실패한 상황을 구분한다.

| 상황             | 대응                      |
| -------------- | ----------------------- |
| 확실한 사건 후보 없음   | 유사 후보 제공 + 탐색 범위 조정     |
| 후보 여러 개        | 가장 유력한 후보 초안 준비 후 필요할 때 Top-3 비교 |
| 가장 유력한 후보에서 위반이 관찰되지 않음 | 음성 결과 + `다른 후보 보기`. 다음 후보를 자동으로 확인하지 않는다(§6) |
| 사건은 맞지만 조금 앞/뒤 | 주변 시간만 재탐색              |
| 차량 특징이 틀림      | 차량 조건 수정 후 재탐색          |
| 번호판 일부 불확실     | 확대 이미지 + 다른 장면 + 직접 입력  |
| 번호판을 읽지 못함     | `알 수 없음` + 경고. 신고자료를 막지 않는다(§12) |
| 발생시각 출처가 약함    | 출처와 주의사항 표시             |
| 위치 근거 없음       | 사용자 기억 유지 또는 UNKNOWN    |
| 신고 상황이 애매함     | 관찰 내용 제시 + `잘 모르겠어요`    |
| 시간 제한 도달       | 현재 범위에서는 보존할 부분 후보가 없다. 실패로 알리고 다시 탐색(새 탐색 의도, §7) |

번호판 판독 **실행 자체의 실패**는 이 표가 아니라 §23의 시스템 실패다.

### 유사 후보만 있는 경우

```text
확실한 사건은 찾지 못했습니다.

다만 기억하신 상황과 비슷한 장면을 찾았습니다.

[유사 후보 보기]
[시간 범위 조정]
[차량 특징 수정]
[상황 다시 설명]
```

### 실제 후보가 하나도 없는 경우

```text
현재 탐색 범위에서는
사건 후보를 찾지 못했습니다.

[탐색 범위 넓히기]
[기억 단서 수정]
```

## `[프로토타입]` 결과 없음 화면에서 지킬 것

**출구를 넷으로 준다.** 「범위 넓히기」 하나만 주면 사용자는 같은 실패를 반복한다.

```text
[앞뒤 30분 더 찾아보기]   ← 기본
[시간을 다시 말할게요]
[차량 특징 고치기]
[비슷하지만 다른 장면 보기]
```

**범위를 넓히기 전에 비용을 미리 말한다.**

```text
영상 9개 → 21개 · 약 4분 더 걸립니다
```

이미 확인한 구간과 새로 확인할 구간을 시간축에 **겹쳐서** 보여준다. 얼마나 더 기다려야 하는지 모른 채 누르게 하지 않는다.

**유사 후보를 진짜 후보와 같은 위계로 두지 않는다.** 「말씀하신 조건과 일부만 맞습니다」를 명시하고, 카드도 후보와 구분되게 표시한다. 섞어두면 사용자는 그중 하나를 정답으로 고른다.

## `[프로토타입]` 「직접 타임라인」 화면은 두지 않는다

1.2 이전 판본(서비스 기획안 1.3 계열)은 결과 0개와 timeout의 출구로 `[직접 타임라인]`을 제시했다. **1.2에서 이미 빠졌고, 프로토타입도 만들지 않았다.** 대신 §6의 「탐색 범위 직접 조정」과 「조건 수정」이 그 자리를 맡는다.

다른 문서에 아직 `[직접 타임라인]`을 전제한 서술이 남아 있다면 그것은 8/27 판본의 잔재다(2026-09-04 확인: `management/cross-cutting-decisions.md` A-1이 이 절을 따른다). 사용자가 영상 타임라인을 직접 훑는 화면이 따로 필요한지는 §26의 미결 항목으로 둔다.

# 23. 시스템 실패 및 복구

AI의 낮은 확신과 시스템 오류를 같은 것으로 취급하지 않는다.

## 분석 실패

```text
영상 분석 중 문제가 발생했습니다.

지금까지 완료된 작업은 저장되어 있습니다.

[다시 시도]
[현재까지의 후보 보기]
```

## 연결 끊김

```text
연결이 끊겼습니다.

작업 상태를 확인하고 있습니다.

[다시 연결]
```

## 지원하지 않는 파일 또는 손상 파일

```text
일부 영상을 처리할 수 없습니다.

FILE_017.mp4
지원하지 않는 형식 또는 손상된 파일입니다.

[다른 영상은 계속 분석]
[파일 확인]
```

## 번호판 판독 실패

번호판을 **읽지 못한 것**(§12, AI가 판독은 했지만 결과가 부족함)과 번호판 판독이 **실행되지 못한 것**은 다르다(#172 D). 뒤쪽은 시스템 실패로 알리고 다시 판독할 출구를 준다. 실행 실패를 「읽지 못함」 결과로 바꿔 경고만 붙인 채 신고자료를 완성하지 않는다.

## 신고용 영상 생성 실패

```text
사건은 찾았지만
신고용 영상 생성에 실패했습니다.

[다시 만들기]
[구간 조정]
```

신고용 영상 생성 실패는 번호판 판독 실패와 별개의 실패다.

가능한 경우 이미 완료된 분석 결과를 보존한다.

`[프로토타입]` **`다시 시도`는 처음부터 다시 돌리지 않고 이어서 진행한다.** 0%부터 다시 돈다면 「지금까지 완료된 작업은 저장되어 있습니다」라는 문장이 거짓이 되고, 이 화면이 존재할 이유도 없어진다.

이 화면은 **제품에서 유일하게 실패색(빨강)을 쓰는 곳**이다. AI의 낮은 확신(§22)은 실패가 아니므로 같은 색을 쓰지 않는다.

# 25. 완료 조건

하나의 사건에 대해 다음 상태에 도달하면 대신고 내부의 신고 준비가 완료된 것으로 본다.

```text
사건 선택
+
가장 유력한 후보 기준 신고자료 초안 준비
+
필요한 신고정보 준비
+
불확실한 값의 상태·출처 표시
+
신고 상황에 대한 사용자 응답
+
문제 항목만 사용자 수정
+
신고 규칙 검사
+
신고용 파생영상 생성
+
신고문 포함 최종 자료 확인
+
사용자 최종 승인
```

이후 안전신문고 제출 단계로 연결한다.

실제 신고 제출은 사용자가 직접 수행한다.

## `[프로토타입]` 흐름의 합격 기준

위 상태에 도달하는 경로가 **네 가지 모두 처음부터 끝까지 끊기지 않아야** 한다. 정상 경로 하나만 되는 것은 완료가 아니다.

1. **정상** — 올리기 → 설명 → 찾기 → 가장 유력한 후보 초안 준비 → 최종 확인 → handoff
2. **후보 변경** — 결과에서 다른 후보 선택 → 새 후보 기준 초안 준비 → 새 결과 확인 → handoff
3. **불확실** — 번호판을 수정하거나, `읽을 수 없음`으로 둔 채 결과 확인 → handoff
4. **복구** — 분석 실패에서 이어서 재시도 / 결과 0개에서 범위를 넓혀 끝까지

# 26. 아직 결정되지 않은 UX 정책

다음 값과 정책은 지금 임의로 고정하지 않는다.

| 항목 | 현재 상태 | 무엇으로 정하는가 |
| --- | --- | --- |
| 가장 유력한 후보 기준 초안 시작 | **결과 중심 흐름으로 채택.** `rank` 또는 후보 정렬 보장, 최신성 검증이 구현 선행 조건. 긴 영상의 클립 분할 탐색은 겹침 길이·중복 제거 호출 지점이 미정(§8-1) | `CaseView` 계약 + 사용자 평가 · 클립 분할 도입 시 search·case |
| 분석 제한시간(timeout)의 실제 값 | 미정 | baseline 실측 후. 담당은 `case`(`modules/case/decisions/timeout-fallback.md`) |
| 사용자 보정·재탐색 횟수와 비용 정책 | 횟수 상한 없음. 자동 후속 탐색이 없어 탐색 비용은 사용자 행동에만 묶여 늘어난다(§6). 비용 상한의 환산·집행 위치는 미정 | 비용·지연 실측 후 · 비용 상한은 search·case |
| 위임 범위 안의 자동 후속 탐색(예: 다음 후보 자동 확인) | 현재 없음(§6) | 자동 후속 탐색 기능과 비용 상한 집행이 생긴 뒤 #170 F 원칙으로 |
| 남은 시간(ETA) 제공 여부 | `[프로토타입]` **제공하지 않음**(퍼센트도 표시하지 않음, §7) | 실측이 쌓인 뒤 재검토 |
| 장시간 분석 완료 알림 방식 | 미정 | — |
| `AI 추정`·`확인 필요` 상태의 결과 표시 | 모든 항목은 결과 페이지에 상태·출처와 함께 표시한다. 사용자는 문제 항목만 수정하며, 중간 확인은 요구하지 않는다 | 사용자 평가 + 신고 규칙 |
| **안전신문고 입력 규칙**(붙여넣기 3 / 직접 고르기 4, §21) | `[프로토타입]` 가정 | **실제 안전신문고 화면 확인 필요** |
| 「직접 타임라인」 화면 필요 여부 | 만들지 않음(§22) | 사용자 평가에서 필요가 드러나면 |

> **가장 위험한 항목은 안전신문고 입력 규칙이다.** 신고유형 분류 이름과 시·분 선택 단위는 실물 화면을 보고 맞춰야 하며, 다르면 §21의 두 묶음 구성과 안내 문구가 함께 바뀐다.

**차량번호 표기 규칙은 확정됐다**(§12). 미결에서 제외한다.

**번호판 `UNKNOWN` 상태에서 신고자료 생성 허용도 결정됐다**(§12, #146 · #172 D-3). 미결에서 제외한다.

`[프로토타입]`에 등장하는 구체적 수치(대기 시간, 보정 폭, 넓히는 범위, 추가 소요 시간)는 **연출값이지 제품 결정이 아니다.** 실제 구현에서 실측으로 대체한다.

이러한 미결 항목의 실제 값과 담당은 각 모듈의 baseline·평가 결과를 근거로 결정하며, 여러 모듈이 관련된 항목은 주간 회의 안건으로 올리고, 결정은 `management/cross-cutting-decisions.md`에 기록한다.

## 27. 기본 구현 후 검토할 후속 아이디어

아래는 지금 구현하거나 완료 기준으로 삼지 않는다. 기본 흐름이 실제로 끝까지 동작한 뒤, 사용자가 정말 필요로 하는지와 처리 시간·비용을 확인하고 별도 작업으로 결정한다.

| 아이디어 | 나중에 검토할 이유 |
| --- | --- |
| 다른 후보 결과를 저장해 두었다가 다시 선택하면 재사용 | 결과 보관 위치·유효 기간·재사용 기준이 필요하다 |
| 후보를 연달아 바꾸기, 원래 후보로 즉시 돌아가기 | 실행 취소·동시 완료·마지막 선택 보호 정책이 필요하다 |
| `내가 승인`과 `나 대신 진행`처럼 중간 확인 방식을 고르는 모드 | 지금의 결과 중심 흐름이 충분한지 먼저 확인한다 |
| 남은 시간 예측, 더 상세한 진행 연출 | 실제 처리 시간 데이터가 쌓인 뒤에만 약속할 수 있다 |

현재 범위에서는 후보를 한 번 바꾸면 새 결과를 준비하고, 준비가 끝난 뒤에만 다시 후보를 고를 수 있다. 결과 이력·재사용·동시 선택은 제공하지 않는다.

## 핵심 정의

대신고는 AI가 법적 판단과 신고를 대신하는 서비스가 아니다.

> **사용자가 기억하는 사건을 설명하면 AI가 장시간 영상 탐색과 신고자료 준비를 대신 수행하고, 불확실하거나 중요한 판단이 필요한 순간에만 사용자에게 확인을 요청하는 인간-AI 협업형 신고 준비 도구다.**

따라서 핵심 사용자 경험은 다음과 같다.

```text
설명
→ 위임
→ AI 작업
→ 결과에서 필요한 항목만 개입
→ 수정 또는 다른 후보 선택
→ 신고자료 완성
→ 사용자 최종 승인
```

AI가 얼마나 많은 기능을 사용하는지가 아니라, **사용자가 얼마나 적은 노력으로 사건을 찾고 신뢰할 수 있는 신고자료까지 도달할 수 있는가**를 중심으로 설계한다.
