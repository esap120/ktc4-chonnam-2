# AI Hub 후보 + sol Fine 토큰 사용량 분석

2026-10-04 · 기존 실제 호출 기록 분석 · 새 모델/API 호출 없음

**가장 큰 원인은 이미지 입력이다.** 최신 LRCN 후보 실험의 총 1,267,644토큰 중 이미지 부분은 공식 계산식으로 약 1,182,816토큰, **93.3%**로 추정된다. 겹치는 후보를 독립 호출하고 5초 후보 앞뒤에 4초씩 붙여 4fps로 전송했다. 정상 클래스가 없는 분류 모델은 정상 영상도 Fine으로 보내게 한다. 프롬프트만 줄이는 것으로는 큰 절감이 어렵다.

근거: `aihub-sol-token-analysis-2026-10-04-results.json` (로컬 보관), [최신 LRCN 실험](aihub-lrcn-sol-fine-2026-10-04.md), [앞선 공간 탐지 실험](aihub-coarse-sol-fine-2026-10-04.md). 실행 경로는 `scripts/aihub_hybrid_fine.py`이고 이미지 추출은 `scripts/gemini_fine_image_accuracy.py`의 `_extract`를 재사용한다.

## 실제 사용량과 추정 분해

API 기록은 입력·출력 합계만 보존한다. 이미지 부분은 이미지 크기·장수와 [OpenAI Docs의 이미지 토큰 계산](https://developers.openai.com/api/docs/guides/images-vision)을 이용한 추정이다. sol의 32px 패치 계산과 1.2 배율을 적용했다. 이번 640×360 및 1280×720 이미지는 high의 축소 한도보다 작아서 별도 축소를 가정하지 않았다. 실제 호출은 detail 생략(auto)이었다.

| 항목 | 공간 탐지 후보 + sol | LRCN 후보 + sol |
|---|---:|---:|
| 호출 | 63 | 51 |
| 이미지 전송 | 3,490장 | 2,390장 |
| 입력 토큰, 실측 | 1,920,752 | 1,243,313 |
| 출력 토큰, 실측 | 41,585 | 24,331 |
| 합계, 실측 | 1,962,337 | 1,267,644 |
| 이미지 입력, 계산 추정 | 1,855,392 | 1,182,816 |
| 이미지가 총 토큰에서 차지하는 비율, 추정 | 94.6% | 93.3% |
| 나머지 입력, 텍스트·스키마·메시지 처리 등 추정 | 65,360 | 60,497 |

실제 프록시의 모달리티별 청구·캐시 적중·추론 토큰 상세는 저장하지 않아 정확히 분리할 수 없다. 위 이미지 계산을 실제 청구 상세와 동일시하지 않는다. 달러 비용도 여기서는 계산하지 않았다. 출력 전체가 최신 합계의 1.9%이고 reasoning은 이미 low여서 출력 길이 축소만으로 입력 비용을 해결하지 못한다.

## 원인 1: 5초 후보가 보통 13초·52장으로 커진다

최신 후보 본문 길이 합계는 255초다. 앞뒤 4초를 붙인 실제 입력 길이 합계는 597.61초로 **2.34배**가 됐다. 추가 342.61초는 전체 전송 길이의 **57.3%**다. 전후 여유가 움직임 판단에 필요한 경우가 있으므로 이 전부를 불필요한 입력이라고 단정하지 않는다.

일반 후보 하나는 `(5초 + 앞4초 + 뒤4초) × 4fps = 52장`이다. 720p에서는 이미지 부분만 `52 × 1,104 = 57,408토큰`으로 추정되고 실제 입력은 약 58,596토큰이다. 작은 후보라도 이미지 수가 빠르게 늘어난다.

## 원인 2: 후보마다 같은 이미지를 다시 보낸다

영상 파일명과 전송 JPEG SHA256을 함께 비교했다. 최신 2,390장 중 서로 다른 이미지는 1,856장이고 **534장 = 22.3%가 다른 호출에서 재전송**됐다. 한 호출 안의 동일 이미지 중복은 0장이다. 해상도별로 가중한 재전송 이미지 토큰은 약 **321,888**이다. 고해상도 중복이 많아 장수 비율보다 이미지 토큰 비중이 크다.

앞선 공간 탐지 실험은 3,490장 중 1,580장, **45.3%가 재전송**이었다. 이미지 토큰 추정으로 약 974,016이다. 유형별로 별도 호출한 것과 후보 앞뒤 여유 구간 중첩이 원인이다.

최신 padded 입력 길이 합계 597.61초에 비해 영상별 시간 합집합은 464.11초다. 같은 시간대를 다른 호출에 여러 번 넣었다. `top2 non-overlapping` 조건은 분류 종류별 후보 본문에만 적용되며, 서로 다른 종류 및 앞뒤 여유 구간의 중복을 막지 않는다. 중복 이미지를 입력에서 무조건 제거하면 시간 순서를 잃을 수 있어, 후보 병합과 명시적 시각·복수 사건 반환을 함께 설계해야 한다.

## 원인 3: 원본 해상도가 높은 영상 몇 개가 비용을 크게 차지한다

720p 설정은 최대 높이이며, 원본이 360p면 그대로다. 실제 최신 입력 크기는 두 종류였다.

| 실제 이미지 크기 | 전송 장수 | 이미지 한 장 계산 추정 | 실측 입력 합계 |
|---|---:|---:|---:|
| 640×360 | 1,784 | 288토큰 | 557,666 |
| 1280×720 | 606 | 1,104토큰 | 685,647 |

720p 이미지는 장수의 25.4%인데 입력 토큰의 **55.2%**를 차지한다. 한 장 비용은 이 두 크기에서 약 **3.83배**다. JPEG 파일 용량과 토큰 수를 혼동하면 안 된다. 원본을 JPEG로 더 강하게 압축하거나 base64 대신 URL로 보내는 것만으로 같은 픽셀 크기의 이미지 토큰 계산을 크게 줄이지는 못한다. base64는 `image_url` 콘텐츠로 전달하며 문자열 전체를 일반 텍스트 프롬프트로 보내는 구조가 아니다.

이전 [해상도 분리 실험](gpt-sol-fine-resolution-window-2026-10-02.md)에서는 720p를 360p로 낮추면 일부 실선 판단 성능이 나빠졌다. 따라서 전체 이미지를 일괄 저해상도로 낮추는 것보다, 전체 장면은 적게 보내고 대상 차량·차선 crop의 실제 세부 픽셀을 유지하는 비교가 필요하다. crop은 그대로 확대하면 절감이 없어질 수 있다.

## 원인 4: LRCN이 정상 영상을 걸러내는 모델이 아니다

정상 3개 영상에서 후보 7개를 sol에 보냈고 입력 **368,219토큰**, 전체 입력의 **29.6%**를 썼다. 모두 720p 원본이다. 분류 점수 0.8 이상이어도 정상 후보가 생겼다. 점수는 세 위반 종류 사이의 상대 점수이며 정상 여부를 확인하는 검출 확률이 아니다. 높은 분류 점수만으로 Fine 호출을 줄이는 것은 검증되지 않았다.

AI Hub 분류·차량·차선 모델은 로컬 실행이라 sol API 토큰을 사용하지 않는다. 비용은 AI Hub 추론 자체보다 그 결과를 후보로 받아 sol에 원본 이미지를 많이 넘기는 단계에서 발생한다. LRCN이 보는 64px 이미지가 sol에 그대로 넘어가는 구조도 아니다.

같은 set1 10개 영상만 보면 이번 Fine은 40회·총 728,674토큰이다. 기존 sol 파이프라인은 Coarse API 비용까지 포함해 회차 평균 497,569토큰이었다. 로컬 Coarse로 바꿔도 Fine 후보를 많이 생성하면 총량은 오히려 약 1.46배가 된다. 후보·Fine 지침·반복 수가 달라 통제 비교는 아니지만, 로컬 모델 도입이 자동으로 토큰 절감을 뜻하지 않는 실제 기록이다.

## 프롬프트와 표시 이미지에 대한 판단

최신 나머지 입력 약 60,497토큰은 총 토큰의 4.8%다. 여기에는 텍스트 외에 응답 JSON 스키마·메시지 처리 등이 포함된다. 이를 전부 절반 줄인다고 가정해도 총 감소는 약 2.4%다. 관찰 정확도를 위한 프롬프트 수정은 필요하지만 주된 토큰 절감 수단은 아니다.

앞서 제안한 원본+차선 표시+crop을 **모든 프레임에 적용하면 비용이 더 늘어난다.** 같은 크기의 표시 이미지 한 장을 매 프레임마다 추가한다고 가정하면 최신 약 127만에서 약 **245만 토큰**으로 증가한다. 동일 크기 3종이면 약 363만이다. 이는 원본·호출 수·나머지 입출력을 유지한 산술 추정이며 실제 추가 프롬프트·응답은 다를 수 있다. 작은 crop과 대표 시각 몇 장만 추가하는 구조는 별도 계산해야 한다.

## 절감 우선순위

1. **겹치는 후보의 중복 호출부터 줄인다.** 같은 영상 구간을 한 번 보고 여러 분류 가설을 함께 확인하게 한다. 긴 병합 구간에서는 복수 사건을 반환할 수 있어야 한다. 이번 확인된 약 32만 재전송 이미지 토큰이 후보지만 전부 절감된다고 보장하지 않는다.
2. **후보 주변 전체에 4fps를 균등 적용하는 대신 실제 움직임 주변에 집중한다.** 일반 구간 1–2fps, 횡단 주변만 4fps 같은 조건을 검출 성능과 함께 비교한다. 4→2fps는 산술적으로 이미지 수를 대략 반으로 줄이지만 실제 위반 순간을 놓칠 수 있다.
3. **고정 앞뒤 4초를 사건별 전후 근거에 맞게 조절한다.** 현재 57.3%가 여유 구간이다. 입력 길이 감소가 검출에 미치는 영향은 재검증해야 한다.
4. **대표 원본·차선 표시 몇 장과 작은 대상 crop을 사용한다.** 전체 프레임을 2·3종으로 복제하지 않는다. crop 대상 식별·신호 맥락을 잃지 않아야 한다.
5. **이미지 장수·예상 토큰에 호출별/영상별 상한을 둔다.** 예산 초과 후보를 단순 삭제하면 미검출이 늘 수 있으므로 우선순위·추가 확인 기준을 함께 평가한다.

위 절감률은 서로 겹치는 원인이므로 더해 계산할 수 없다. 성능을 유지하는 절감 설정은 아직 실행하지 않았다. 이번 작업은 기존 호출 수·영상 길이·원본 크기·이미지 해시·API 사용량을 대조한 분석이며 운영 코드와 실험 조건은 변경하지 않았다.
