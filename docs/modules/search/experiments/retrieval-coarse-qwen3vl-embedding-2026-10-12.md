# Retrieval Coarse — Qwen3-VL-Embedding 영상 창 임베딩

작성일: 2026-10-12. 상태: **완료 — 신호 부족(Recall@3 3/11, 무작위 95백분위 3 이하)**. [#279](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/issues/279) 실험 B의 후속이다. 로컬 RTX 3060에서만 실행하며 유료 API 호출·운영 코드 변경·모델 학습은 없다.

## 1. 왜 하나

[v1](retrieval-coarse-preflight-2026-10-11.md)·[v2](retrieval-coarse-v2-2026-10-11.md)는 프레임 한 장 단위의 이미지·문장 모델(SigLIP)이었다. 「선에 걸친 차」를 정상 주행과 구분하지 못했고, 움직임은 원래 볼 수 없었다.

이번에는 **여러 프레임을 묶은 짧은 영상 창**을 하나의 벡터로 만드는 모델을 쓴다. 질문은 하나다. **영상 단위 임베딩이면 사건 위치에 대한 신호가 v1보다 나아지는가.**

모델은 `Qwen/Qwen3-VL-Embedding-2B`(2026-01 공개, 영상 이해 모델 Qwen3-VL 기반 임베딩, 약 4GB)다. 같은 계열 API인 Gemini Embedding 2는 현재 Elice 키의 모델 목록에 없어(2026-10-12 `/models` 조회: `gemini-3.8-flash`만) 쓰지 않는다.

v1·v2 결과를 이미 본 뒤의 실험이다. 다만 이번에 바꾸는 것은 **모델과 입력 단위뿐**이고 문장은 v1을 그대로 쓴다.

## 2. 조건 (실행 전 고정)

| 항목 | 값 |
| --- | --- |
| 모델 | `Qwen/Qwen3-VL-Embedding-2B`, bf16, 공식 `scripts/qwen3_vl_embedding.py`의 `Qwen3VLEmbedder` |
| 데이터 | v1과 같은 set1 13클립(양성 10클립·11사건, 정상 3클립) |
| 프레임 | ffmpeg `-map 0:v:0 -vf fps=2,scale=640:-2`. 프레임 i의 시각 = i × 0.5초. 폭 640(운영 Coarse 360p와 비슷한 크기) |
| 창 | 길이 4초, 보폭 1초. 마지막 창은 영상 끝에 맞춘다. 창 하나 = 프레임 8장을 영상(frame list)으로 입력 |
| 영상 쪽 지시문 | 기본값 `Represent the user's input.` |
| 문장 쪽 지시문 | `Retrieve dashcam video clips that show the described traffic event.` |
| 문장 | v1과 같은 3개 (아래) |
| 점수 | 창 임베딩과 문장 임베딩의 cosine |
| 평활 | 없음(창이 이미 4초를 묶는다) |
| 유형 간 정규화 | v1과 같다. 유형마다 13클립 전체 창의 평균·표준편차로 z |
| 후보 | 창 하나 = 후보 하나([창 시작, 창 시작+4]). 유형마다 z 높은 창부터, 같은 유형에서 이미 고른 창과 겹치면 건너뛴다. 유형당 최대 5개 |
| 순위·채점·기준선 | v1과 같다(`vc3_score` 재사용, 엄격 겹침, 무작위 위치·순위 섞기 각 10,000회) |

| 유형 | 문장 |
| --- | --- |
| `SOLID_LINE_LANE_CHANGE` | a vehicle changes lanes by crossing a solid white lane line |
| `CENTER_LINE_CROSSING` | a vehicle crosses the center line into the opposite lane |
| `SIGNAL` | a vehicle drives through the intersection while the traffic light is red |

공식 스크립트는 frame list를 기본 64장으로 늘려 샘플링한다. 창마다 실제 8장만 넣도록 `num_frames=8, max_frames=8`로 둔다.

## 3. 판단 기준 (실행 전 고정)

v1 §5와 같다.

| 결과 | 해석 |
| --- | --- |
| 판단용 3유형 Recall@3 > 무작위 95백분위 **그리고** ≥5/11 | A — 신호 확인. 정식 challenger 확장 검토를 주간 회의 안건으로 |
| 무작위 95백분위 초과, 5/11 미만 | 약한 신호. 결과만 보고 |
| 무작위 95백분위 이하 | 신호 부족 |

v1(4/11)과의 1–2건 차이는 우연과 구분하지 않는다.

## 4. 한계

- set1은 반복 사용한 개발 데이터이고 정상은 3클립뿐이다.
- 문장은 v1 그대로라 문구 민감도를 보지 않는다.
- 2B 모델 1종이다. 8B는 3060 메모리에 맞지 않을 수 있어 보지 않는다.
- 창 4초·2fps(8장)는 정답 사건 길이(1–4초)에 맞춘 값이다. 다른 창 길이는 보지 않는다.

## 5. 결과 (2026-10-12 실행)

실행: 13클립 585창 × 문장 3개, 1회. 누락 클립 0. 프레임 추출·임베딩 합계 305.7초(모델 로드 제외, 원본 약 620초의 0.5배), 피크 VRAM 4.21GiB. 로컬 `.omc/retrieval/runs/sims_qv.jsonl`, 채점 `runs/score_qv.json`.

| 조건 | Recall@1 | **Recall@3** | Recall@5 | 전체 후보 겹침 | 무작위 Recall@3 평균 / 95백분위 / P(≥관측) | 순위 섞기 95백분위 / P(≥관측) |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| **3유형 — 판단용** | 2/11 | **3/11** | 3/11 | 5/11 | 1.66 / 3 / 0.17 | 3 / 0.09 |
| 정답 유형 — 참고 | 2/11 | 4/11 | 5/11 | 5/11 | 3.62 / 6 / 0.51 | 5 / 0.50 |
| 참고: SigLIP v1 3유형 | 3/11 | 4/11 | 6/11 | 8/11 | 1.30 / 3 / 0.019 | 4 / 0.084 |

사건별 첫 적중 순위(3유형): C08 **1** · C33 2 · C39 **1** · C00 8 · C28 13, 나머지 6건 없음. 적중 후보의 시각 오차는 0–3초.

**판단: 신호 부족.** 판단용 Recall@3 3/11은 무작위 위치 95백분위(3)를 넘지 못한다(같음). v1(4/11)과의 차이는 1건이라 우연과 구분하지 않는다. 영상 단위 임베딩으로 바꿔도 v1보다 나아지지 않았다.

관찰 (판단에 쓰지 않음):

- **신호위반은 이번에도 잡혔다.** C08 rank1, C33 rank2. v1·v2 진단과 같은 경향이다.
- **차선 위반은 C39 하나만 rank1로 새로 맞았고, v1에서 맞던 C10·C44는 놓쳤다.** 실선 7건 중 상위 3개 적중은 1건이다.
- **정상 클립에서 「차로 변경 장면」 자체는 짚었다.** 합법 점선 변경 클립 `141956`의 최고 후보가 정답지의 점선 변경 구간(≈10–14초)과 같은 10–14초 창이었다(중앙선·실선 문장 모두). `141628`의 최고 후보 0–4초는 정답지에서 「앞차가 오른쪽으로 이동하는 듯 보이나 정지 프레임으로는 구분 불가」로 남긴 구간이다. 영상 임베딩이 차로 변경 같은 움직임에는 반응하지만 실선·점선(위반 여부)은 가리지 못한다는 해석과 맞는다. 사례 2건뿐이고 정답지 채점 대상이 아니라 확인되지 않은 관찰이다.
- 양성 클립 상위 3개 중 라벨과 다른 유형 후보가 19개다. 유형 문장 사이 구분이 약하다.

### 해석

- 프레임 단위(SigLIP)든 4초 영상 단위(Qwen3-VL-Embedding)든, 범용 임베딩 retrieval로는 차선 위반의 위치 신호를 무작위와 구분해 얻지 못했다.
- 「차로 변경이 일어나는 구간」을 찾는 용도라면 가능성이 보이지만, 이번 정답지는 위반 사건만 표시하므로 그 용도는 측정하지 않았다. 측정하려면 합법 차로 변경까지 표시한 정답지가 필요하다.
