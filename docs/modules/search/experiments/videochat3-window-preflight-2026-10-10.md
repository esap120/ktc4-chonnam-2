# 실험 3 — VideoChat3-4B 3060 사전검증: 12초 창 분할 Coarse 신호 확인

작성일: 2026-10-10. 상태: **완료 — 판단 C(신호 부족)**. [#279](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/issues/279) 실험 C(VideoChat3 local preflight)의 후속이다. 로컬 RTX 3060 12GB에서만 실행하며 유료 API 호출·운영 코드 변경·모델 학습은 없다.

이 실험은 `challenger-policy.md`의 **챌린저 개방이 아니다.** 개방은 주간 회의 안건·PM 승인 절차를 따르며, 이 문서의 결과는 그 안건의 근거로 쓴다. [#283](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/pull/283)이 제안한 순서(CV_LANE_TRACK → Retrieval → VideoChat3)와 병행하므로 회의에서 순서 변경 여부를 함께 확인한다.

## 1. 선행 결과 — C1 smoke·scaling (2026-10-10 실행)

환경: Windows 11, RTX 3060 12GB, torch 2.6.0+cu124, transformers 4.57.6, `MCG-NJU/VideoChat3-4B` bf16(로드 후 8.33GiB, 여유 2.64GiB). flash-attn 미설치. 비전 인코더의 공식 sdpa 경로는 전체 패치 수² 마스크를 만들므로 **세그먼트 안에서만 attend하는 동일 계산**으로 교체했다. 프롬프트는 공식 TimeLens grounding 문구, greedy, `max_new_tokens=128`.

> **정정 (2026-10-10):** 첫 측정은 교체한 attention 함수의 버그 상태였다. 3차원 텐서를 넘겨 PyTorch가 memory-efficient 커널 대신 N² math 경로를 사용했다. 4차원으로 고친 뒤 참조 계산과 bf16 오차(최대 0.002) 내에서 일치했고, 아래 표는 **수정 후 재측정**이다. 수정 전 값은 괄호로 남긴다.

관찰:

- attention 수정으로 비전 인코딩은 빨라졌지만(15초 창 66→13초), **입력 토큰 약 4,000 이상에서는 피크 VRAM이 수정 전과 같다.** 60s·2fps OOM 시 추가 요청량 7.41GiB는 언어 모델 attention 점수 행렬(32 head × 7,883² × 4바이트)과 일치한다. 언어 모델 쪽도 Windows torch에서 fused 커널을 쓰지 못하고 N² 경로로 계산하는 것으로 본다(원인 미확정).
- 따라서 60초 클립 OOM은 모델 고유의 요구량이 아니라 **이 환경(Windows·flash-attn 없음)의 구현 한계**다. 큰 GPU의 필요성 근거로 쓰지 않는다. flash-attn이 되는 Linux 환경에서는 다를 수 있으며 측정하지 않았다.
- 448²·60프레임의 답이 커널 변경만으로 12–14s → 1–3s·30–32s로 바뀌었다. bf16 수치 차이에 답이 민감하며, 수정 전 답이 정답 근처였던 것은 신호로 보기 어렵다. 15초 창과 224² 답은 바뀌지 않았다.
- 224²는 빠르지만 답이 정답에서 20초 이상 벗어났다.
- 질문 유형은 정답 라벨을 보고 골랐다. scaling 측정용이며 성능 근거로 쓰지 않는다.
- 4프레임이 하나의 토큰 묶음이 되므로 2fps에서 시간 해상도는 약 2초다.

## 2. 질문과 가설

**질문:** 3060에서 실행 가능한 축소 조건(창 분할·2fps·448²)에서 VideoChat3가 set1 사건 위치에 대해 무작위보다 나은 신호를 내는가? 낸다면 Gemini Flash Coarse와 비교해 어느 수준인가?

- **H1:** 창 단위 grounding 후보의 Recall@3이 같은 길이 무작위 후보의 95백분위를 넘는다.
- **H2:** 창별 존재 확률(P(Yes))로 정렬한 순위가 같은 후보를 무작위로 정렬한 순위보다 Recall@3이 높다.
- **H3:** 정상 3클립에서도 후보가 생긴다. grounding 프롬프트는 항상 구간을 반환하므로, 오탐 억제는 존재 확률 순위에 달려 있다.

#279 판단 기준 B·C를 가르는 것이 목적이다. 정식 challenger 성능 비교가 아니며 결과를 Gemini 대비 우열 근거로 쓰지 않는다.

## 4. 조건

| 항목 | 값 |
| --- | --- |
| 창 | 길이 W초, 보폭 W/2. 마지막 창은 영상 끝에 맞춘다. W는 §5 보정 단계에서 고정 |
| 창 입력 | ffmpeg로 재인코딩해 잘라 낸 별도 파일. 모델 시각은 창 기준이므로 창 시작 시각을 더해 원본 초로 환산 |
| 샘플링 | 2fps, 프레임 최대 448²(공식 기본값). 축소는 창 길이로만 한다 |
| 질문 | 모든 창에 3유형을 모두 넣는다. 정답 유형을 고르지 않는다 |
| 생성 | greedy, grounding `max_new_tokens=128`, 존재 질문은 첫 토큰 logit만 사용 |

질문 문구는 실행 전에 고정하고 결과를 본 뒤 바꾸지 않는다.

| 유형 | `{query}` |
| --- | --- |
| `SOLID_LINE_LANE_CHANGE` | a vehicle changes lanes by crossing a solid white lane line |
| `CENTER_LINE_CROSSING` | a vehicle crosses the center line into the opposite lane |
| `SIGNAL` | a vehicle drives through the intersection while the traffic light is red |

창마다 유형별로 질문 2개를 보낸다.

1. **grounding (구간):** 공식 TimeLens 문구 그대로. `Please find the visual event described by the sentence '{query}', determining its starting and ending times. The format should be: 'The event happens in <start time> - <end time> seconds'.`
2. **존재 (점수):** `Does this video show the following event: '{query}'? Answer Yes or No.` 첫 생성 위치의 `Yes`/`No` 토큰 logit 두 개에 softmax를 적용해 P(Yes)를 점수로 쓴다.

헬멧 미착용은 set1에 양성이 없어 제외한다.

**채점 조건 2개 (같은 실행 결과에서 계산):** 질문은 서로 독립 호출이므로 추가 실행 없이 채점만 달리한다.

| 조건 | 후보로 쓰는 유형 | 역할 |
| --- | --- | --- |
| **3유형 — 판단용** | 모든 클립에서 3유형 전부 | §7 판단 기준 적용 |
| 정답 유형 — 참고 | 양성은 라벨 유형만, 정상은 실선만 (Flash A와 같은 규칙) | Flash A(14/33)와 조건을 맞춘 참고 비교. 판단에 쓰지 않음 |

**실측 입력 형식:** 12초 창 2fps에서 실제 샘플링은 4의 배수로 맞춰지고 4프레임이 묶여, 모델이 보는 시간 표시는 약 2.2초 간격 7개 안팎이다(예: 15초 창 `<0.8> <3.0> <5.3> <7.5> <9.7> <11.9> <14.1 seconds>`). 시각 오차 약 2초는 구조상 하한이다.

**비전 인코딩 재사용:** 창의 비전 특징은 질문과 무관하므로 창마다 한 번만 계산하고 6개 질문에 재사용한다(`get_video_features` 결과 캐시). 실행 전 창 2개에서 캐시 사용·미사용 응답과 logit이 같은지 확인한다. 다르면 캐시 없이 실행한다.

## 6. 후보·순위·지표

**후보:** grounding 답 1개 = 후보 1개. 창 밖이거나 파싱 실패면 `CANDIDATE_INVALID`로 기록하고 후보에서 제외한다. 점수는 같은 창·유형의 P(Yes)다. 같은 유형 후보끼리 본문이 겹치면 점수가 높은 것만 남긴다.

**순위:** 클립의 모든 유형 후보를 점수 내림차순으로 정렬한다. 정답 유형만 먼저 골라 다시 순위를 매기지 않는다.

**적중:** 정답 유형 후보이고 `candidate.start < truth.end`와 `truth.start < candidate.end`를 모두 만족. padding 없음. 경계 접촉은 비적중.

| 지표 | 정의 |
| --- | --- |
| **Recall@3 — 주 지표** | 상위 3개 안 적중 사건 수 n/11 |
| Recall@1 · @5 | 같은 방식 |
| 전체 후보 겹침 | 순위와 무관하게 적중 후보가 있는 사건 수 n/11. Flash의 「Coarse 겹침」과 대응 |
| 시각 오차 | 적중 후보 중점과 정답 onset의 절댓값 차이, 중앙값·최대 |
| 정상 후보 | 정상 3클립의 상위 3개 점수 분포, P(Yes) ≥0.5 후보 수 |
| 유형 혼동 | 양성 클립에서 라벨과 다른 유형의 상위 후보 수. 미라벨 사건 가능성이 있어 확정 오탐과 구분 |
| 처리량 | 창당 비전·질문별 시간, 전체 wall-clock, 피크 VRAM |
| 실패 | 파싱 실패·창 밖 구간·OOM 수 |

**기준선:**

| 기준선 | 의미 |
| --- | --- |
| 무작위 구간 | 클립마다 VideoChat3 후보와 같은 길이의 구간을 균일하게 K개 배치, 10,000회 시뮬레이션. Recall@3 평균·95백분위 |
| 점수 섞기 | VideoChat3 후보 그대로, 순위만 무작위 10,000회. P(Yes) 순위의 효과(H2) |
| Flash 실험 1 | 1유형(정답 유형 제공) Coarse 겹침 14/33, 4유형 7/33. 3유형을 모두 넣는 이번 조건은 4유형 쪽에 가깝다. 전송·해상도·모델이 달라 참고 비교만 |

- 정상 3클립은 오탐률 근거로 부족하다. 사건 없는 113개 조각은 미확보다.
- 11사건·1회 실행이라 1–2건 차이는 우연과 구분되지 않는다.
