> Execute inline on the approved `feature/runtime-job-claim-finish` branch. User approved the design and execution, with NOW(6)/UTC sessions and no STALE finish. No commits, pushes or PR creation.

**Goal:** Short durable claim and caller-owned terminal finish for Issue #290.
**Architecture:** Covering ID SELECT SKIP LOCKED, conditional UPDATE, PK snapshot, acknowledged commit. A nullable private claim_token and a pinned execution ID identify one public call across RT-02 retries. Finish participates in the caller's transaction.
**Tech Stack:** SQLAlchemy Core, PyMySQL, Alembic, real MySQL 8.4.
**Spec:** User-approved chat design and amendments; Runtime Plan §6 RT-03 and §12, Tech Spec §4.2/4.3/4.5/6.3/12.1/12.4, JobExecution Contract §4–6/9, B-W3/B-L2/B-L6, S1/S2.

## Global Constraints

- Use DB NOW(6) for claim eligibility and lease, with UTC application/worker sessions. No Baseline changes.
- Finish targets SUCCEEDED/FAILED/CANCELLED only; CANCELLED produced must be empty.
- Never modify runtime_0001, Case-owned files, protected JSON or existing pytest scratch folders.
- Claim callback has no INSERT/handler/external I/O. Return only after acknowledged commit.
- Unknown commit recovery reads the same execution ID/token; mismatch/lost/terminal is an error, not an empty queue.
- No worker loop/heartbeat/cancel requests/STALE sweep/new attempts/usage/HTTP.
- Keep RT-03 IN_PROGRESS until independent re-review. Preserve evidence outside existing scratch folders.

## Review Focus

- Same worker ID in independent invocations: distinguish receipt tokens.
- Recycled/reused sessions: UTC must survive connection replacement and timezone contamination.
- Acknowledged commits and observability failures: neither may cause a duplicate retry.
- Stale snapshots in finish: conditional UPDATE must decide races, not prior reads.
- Unknown commit followed by expired or terminal receipt: never dispatch or claim another row.
